# Acceptance Criteria

## Every lab

- Has one certificate and one clearly stated learning objective.
- Has its own stable route and direct URL.
- Performs a real input-to-output workflow.
- Includes realistic, non-sensitive sample data.
- Validates missing, malformed, and out-of-range input.
- Provides reset and example actions.
- Works without paid services, private credentials, or mandatory API keys.
- Has focused automated tests for its core calculation or transformation.
- Has keyboard-usable controls and readable labels.
- Works at desktop and mobile widths.
- Documents its algorithm, limitations, and certificate connection.
- Contains no claims of real-world impact that were not measured.

## Security labs

- Defensive and educational only.
- No credential collection, stealth, persistence, exploitation, or unauthorized scanning.
- Uploaded data remains local to the browser unless explicitly documented and approved.
- Includes a visible scope and safety statement.

## Flagship applications

- Core workflow passes end-to-end smoke tests.
- Uses sanitized demo data in public deployments.
- Has a health endpoint or verifiable public status route.
- Builds from a locked dependency graph.
- Includes deployment and rollback documentation.
- Has a stable public URL and repository evidence.

## Batch completion gate

1. Requirements mapped to tests.
2. Unit tests pass.
3. Integration or smoke tests pass.
4. Production build passes.
5. Desktop and mobile workflows verified.
6. Accessibility basics verified.
7. Security/privacy review completed.
8. Documentation updated.
9. Known limitations recorded.
10. Git checkpoint created only after the first nine items pass.

## Final visual gate

Visual polish is a later phase. Final delivery additionally requires an approved visual concept, browser screenshots at desktop and mobile sizes, direct comparison with the approved concept, and no visible layout defects.
